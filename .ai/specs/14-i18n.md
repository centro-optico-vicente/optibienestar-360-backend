# 14 — Internacionalización (i18n) y locale runtime

> Spring i18n + bundles `messages_*` / `ValidationMessages_*`. Idiomas soportados: `es` (defecto operativo: `es-VE` per [ADR 0010](../decisions/0010-localization-venezuela.md)) y `en` (fallback canónico, sirve para logs técnicos y locales fuera de whitelist).
>
> **Principio:** todo texto user-facing va por **MessageSource code**, nunca como string literal en código Java. El bundle es la única fuente de verdad para mensajes; mover un string a otro idioma cuesta una entrada en un `.properties`, no un cambio de código.

## Cadena de fallback del locale (resolver)

Implementada en `core/config/HybridLocaleResolver` (extiende `AcceptHeaderLocaleResolver`):

1. **Claim JWT `locale`** — si el principal autenticado tiene `CustomUserDetails.getLocale()` no-vacío y está en la whitelist (`es`, `en`), gana.
2. **Header `Accept-Language`** — solo si pertenece a la whitelist; lookups por *base language* (`es-MX`, `es-ES` → `es`).
3. **Default app** — `es-VE` (configurado en `spring.web.locale`).

Cualquier locale fuera de la whitelist (ej. `pt-BR`) cae al siguiente nivel. Esto evita que un `Accept-Language` arbitrario cargue un bundle inexistente y rompa el response.

```
[ JWT claim "locale" ] → [ Accept-Language ] → [ es-VE default ]
   prioridad 1              prioridad 2          prioridad 3
```

## Convención de naming de claves

**Dot-separated**, agrupado por dominio:

```
<dominio>.<sub-grupo>.<concepto>[.<estado>]
```

Ejemplos del backend:
- `auth.credentials.invalid`
- `auth.token.refresh.invalid`
- `auth.password.history.repeat`
- `user.not_found`
- `user.email.exists`
- `role.system.not_editable`
- `role.permission.uuid.unknown`
- `validation.document_type.format`
- `validation.code.uppercase.short`
- `error.title.unauthorized`
- `error.detail.access_denied`
- `email.recovery.subject`

Reglas:
- `snake_case` dentro de cada segmento (no camelCase ni guion).
- Dominio coincide con el módulo (`auth`, `user`, `role`, `email`, `validation`, `error`).
- Claves de *validación Jakarta Bean* van con prefijo `validation.` y entre llaves dentro del `@Pattern`/`@Size`/etc.: `message = "{validation.code.uppercase.long}"`.
- Claves del `GlobalExceptionHandler` para títulos y detalles genéricos llevan prefijo `error.title.*` / `error.detail.*`.

## Patrón base + extends (bundles)

Cada bundle tiene 3 archivos:

| Archivo | Rol |
|---|---|
| `messages.properties` | **Fallback canónico en inglés.** Lo lee Spring cuando el locale del request no matchea `es*` ni `en*`. Mantiene TODAS las claves. |
| `messages_es.properties` | Texto en español (es-VE neutro). Resuelve para cualquier `es*` por fallback estándar de `ResourceBundle` (`es-VE → es → default`). |
| `messages_en.properties` | Texto en inglés. Sirve cuando el header/claim es `en*` explícito. |

Análogo para `ValidationMessages*.properties`. **No** se crean variantes `_es_VE` — el fallback de ResourceBundle ya cubre `es-VE → es`. Crear una variante regional solo si en el futuro un dialecto difiere materialmente.

Configurado en `application.properties`:
```properties
spring.messages.basename=messages,ValidationMessages
spring.messages.encoding=UTF-8
spring.messages.fallback-to-system-locale=false
```

Bundles vivos en `src/main/resources/`.

## Patrones de uso

### 1. Excepciones de negocio — `LocalizedBusinessException`

Para errores de negocio propios, heredar de `core/exception/LocalizedBusinessException` y pasar `messageCode` + `args` opcionales.

```java
public class AuthenticationException extends LocalizedBusinessException {
    public AuthenticationException(String code, Object... args) {
        super(code, args);
    }
}

// uso:
throw new AuthenticationException("auth.credentials.invalid");
throw new AuthenticationException("auth.password.history.repeat");
```

`GlobalExceptionHandler.resolveLocalized(lbe, locale)` resuelve el code vía MessageSource y arma el `ProblemDetail`.

### 2. Excepciones JDK/Spring — code como mensaje

Para excepciones que NO controlamos (`IllegalArgumentException`, `NoSuchElementException`, `AccessDeniedException`), lanzamos con el **code como mensaje** y el handler lo detecta:

```java
throw new NoSuchElementException("user.not_found");
throw new IllegalArgumentException("role.auto_lockout");
throw new AccessDeniedException("role.system.not_editable");
```

`GlobalExceptionHandler.resolveCodeOrLiteral(msg, locale)` intenta resolver `msg` como code; si está en el bundle devuelve la traducción, si no devuelve el literal. Esto es **graceful para mensajes legacy** (excepciones viejas con mensaje en inglés siguen funcionando sin romper).

### 3. Validación Jakarta Bean — `@Pattern(message="{code}")`

```java
public record AdminCreateUserRequest(
    @NotBlank @Email String email,
    @Pattern(regexp = "^[VE]$", message = "{validation.document_type.format}")
    String documentType,
    ...
) {}
```

Las llaves `{...}` activan la resolución vía `LocalValidatorFactoryBean` configurado contra el mismo MessageSource. Spring Boot lo autoconfigura cuando `spring.messages.basename` incluye `ValidationMessages`.

### 4. Inyección directa de MessageSource — caller controlado

Para casos sin excepción (subject de email, label en respuesta, etc.):

```java
@RequiredArgsConstructor
public class AuthService {
    private final MessageSource messageSource;

    public void recoverPassword(...) {
        Locale recipient = resolveRecipientLocale(user);  // user.getLocale() → fallback es-VE
        String subject = messageSource.getMessage("email.recovery.subject",
                                                  new Object[]{appName}, recipient);
        emailService.sendTemplated(user.getEmail(), subject, "password-recovery",
                                   recipient, vars);
    }
}
```

## Templates email — locale del destinatario, no del request

Regla operativa: **el email va en el idioma del usuario que lo recibe**, no en el del que disparó el flujo.

- `AuthService.recoverPassword` — resuelve locale desde `user.getLocale()` con fallback a `es-VE`. Si admin (en sesión `en`) dispara reset para un afiliado con `locale=es`, el email va en español.
- `ContactService.submit` — endpoint público sin auth, usa `LocaleContextHolder.getLocale()` (lo único disponible).

Convención de archivos:
- `templates/<name>.html` — fallback EN (`lang="en"`).
- `templates/<name>_es.html` — español.
- `templates/<name>_en.html` — inglés explícito.

`EmailService.sendTemplated(to, subject, template, locale, vars)` resuelve `template_<lang>.html` por whitelist (`{es, en}`), instancia `new Context(locale)` para que cualquier `#{key}` en el template resuelva contra MessageSource.

## Locale persistente del usuario

- `users.locale VARCHAR(10)` — preferencia del usuario (nullable; null = usa default app).
- `countries.locale VARCHAR(10)` — locale canónico del país (seed `VE='es-VE'`); útil para inicializar `users.locale` en registro.
- `user_sessions_log.login_locale VARCHAR(10)` — **snapshot inmutable** del locale efectivo al momento del login (analytics/forensics).

**JWT claim `locale`** — `JwtService.generateAccessToken(subject, permissions, locale)` lo emite solo si no es null/blank. El refresh token NO lo lleva (la preferencia puede haber cambiado entre access y refresh).

**Cambio mid-session (Option C):** `POST /v1/me/locale` con `LocalePreferenceRequest`:
1. Actualiza `users.locale`.
2. Reemite access token nuevo con claim `locale` actualizado.
3. Blacklistea el access token anterior (efecto inmediato).
4. **NO rota refresh** — cambiar idioma no es un evento de seguridad.

Devuelve `AccessTokenResponse` con el token nuevo. El frontend reemplaza el access en su storage sin tener que re-loguear.

## Cómo agregar un idioma nuevo

Ejemplo: agregar **portugués** (`pt`).

1. **Whitelist resolver** — en `HybridLocaleResolver`, agregar `Locale.forLanguageTag("pt")` a `supportedLocales`. Si la whitelist también está en `LocalePreferenceRequest` (`@Pattern`), actualizar la regex.
2. **Bundles** — crear `messages_pt.properties` y `ValidationMessages_pt.properties` con TODAS las claves traducidas. Usar `messages.properties` (EN canónico) como base.
3. **Templates email** — crear `<name>_pt.html` para cada template. Ajustar la whitelist en `EmailService.sendTemplated`.
4. **Seed opcional** — si hay un país pt-hablante en `countries`, setear `countries.locale='pt-BR'` (o lo que aplique) para que usuarios nuevos hereden la preferencia.
5. **Tests** — agregar caso en `I18nConfigTest` que verifique resolución de una clave en el nuevo locale.

**No** hace falta tocar:
- `GlobalExceptionHandler` (resuelve automáticamente cualquier locale soportado).
- Anotaciones `@Pattern(message="{code}")` (idem).
- `MessageSource` config (reload automático mientras el archivo esté en classpath).

## ¿Cuándo crear `LocalizedBusinessException` nuevo vs reusar?

| Situación | Hacer |
|---|---|
| Error de negocio recurrente con semántica propia (ej. password reuse, account locked) | **Subclase de `LocalizedBusinessException`** con HTTP status implícito en el handler. |
| Validación de input que se mapea naturalmente a `IllegalArgumentException` | **Reusar** `IllegalArgumentException`, mensaje = code. Status 422. |
| Recurso no encontrado | **Reusar** `NoSuchElementException`, mensaje = code. Status 404. |
| Falla de autorización dependiente de runtime (no Spring Security) | **Reusar** `AccessDeniedException`, mensaje = code. Status 403. |
| Error técnico interno (Redis caído, DB violation no semántica) | Lanzar **sin code** (mensaje técnico en EN); el handler cae al fallback 500 con detalle genérico. |

Crear una subclase nueva **solo si** el flujo tiene status HTTP único o requiere lógica especial en el handler (ej. `AccountLockedException` → 423 Locked). En el resto, el patrón "code en `getMessage()`" es suficiente.
