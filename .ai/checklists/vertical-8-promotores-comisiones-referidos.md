### Ítem PDF #2 — Manejo de Descuentos por Referidos (con metas)

> **⚠️ Superseded parcialmente por v3 (Ítem C, más abajo).** El diseño de recompensa por referido se concreta en v3 como **salto de mensualidad** (subsidio `monthly_percentage=100`, reusa V41) en lugar del reward "10% off 1 pago FIFO". La tabla `referral_reward_programs` (v3) refina este `referral_programs`. ## Pendientes de análisis / Decisiones diferidas

> **Doctrina general del proyecto**: ver [`../specs/02-database.md` § Decisiones diferidas y pendientes de análisis](../specs/02-database.md#decisiones-diferidas-y-pendientes-de-análisis). Esta sección lista los items específicos que dejaron las migraciones de esta vertical; el spec mantiene el índice cross-vertical para trazabilidad.

### V25 — `promoters`

- [ ] [diferido] **Snapshot counters `promoters.total_referrals` + `total_commission_paid`**: ¿se actualizan vía TRIGGER en `commissions` (más simple pero acopla schemas) o vía service code en el `CommissionService` cuando una commission pasa a `PAID` (más explícito, permite batch + reintentos)? **Trigger de cierre**: definir antes de implementar `PUT /v1/admin/commissions/{uuid}/mark-paid` o el batch de payout, ese es el momento natural en que el counter avanza.
- [ ] [diferido] **Sincronización `promoters.display_name` ↔ `persons.full_name`**: hoy se setea al crear el promotor (default `person.full_name`) pero NO se mantiene sincronizado si el `Person` se edita después. ¿Es deseado divergir (admin puede personalizar) o sincronizar al cambiar el Person? **Trigger de cierre**: surge cuando aparezca un caso real de admin que pide editar el nombre del promotor sin tocar el Person.
- [ ] [diferido] **Workflow de `promoters.status=SUSPENDED`**: el CHECK constraint lo permite (ACTIVE/INACTIVE/SUSPENDED) pero **no hay endpoint que lo aplique**. **Trigger de cierre**: agregar `PUT /v1/admin/promoters/{uuid}/suspend` con razón obligatoria cuando aparezca el caso de uso real (fraude detectado, contrato terminado). Hasta entonces, INACTIVE vía soft-delete cubre el flow.
- [x] [resuelto 2026-08-06] **`members.promoter_id` schema NULLABLE vs service NOT NULL**: resuelto a favor de NULLABLE real — se removió el enforce NOT NULL/fallback INSTITUCION de `PromoterResolver.resolveForEnrollment`. Un afiliado puede quedar sin promotor al crear y vincularse después vía `assign-promoter` (acepta `promoterUuid` o `referralCode`). Las comisiones siguen resolviendo INSTITUCION a nivel de cálculo (`CommissionService.resolvePromoter`), así que este campo controla solo la atribución *mostrada*, no el flujo de comisiones.

### V26 — `commissions`

- [ ] [diferido] **FK `commissions.commission_tier_id` → `commission_tiers`**: la columna existe como BIGINT sin REFERENCES porque la tabla `commission_tiers` no existe todavía (planeada v2). **Trigger de cierre**: cuando llegue V27+ con `commission_tiers`, agregar `ALTER TABLE commissions ADD CONSTRAINT fk_commissions_tier FOREIGN KEY (commission_tier_id) REFERENCES commission_tiers(commission_tiers_id);` al final de esa migración (mismo patrón que el FK diferido V18→V23 de `beneficiaries.inscription_payment_id`).
- [ ] [diferido] **Tabla `commission_payouts` futura vs `payout_reference VARCHAR` actual**: hoy el row de commission referencia el cobro batch via string libre. ¿Vale la pena promover a tabla `commission_payouts` (uuid, executed_at, total_amount, currency, bank_reference, ...) cuando aparezca el bullet de "cierre de período + CSV + email promotor"? Si sí, migrar `payout_reference` a `payout_id BIGINT FK`. **Trigger de cierre**: análisis al implementar `POST /v1/admin/commissions/payout`.
- [ ] [diferido] **Política de void: VOIDED row vs commission negativa**: cuando un payment se revierte/refunda, las commissions tied a él necesitan compensación. **Opción A** — VOIDED status sobre el row original (audit limpio, una sola fila por evento). **Opción B** — nueva fila con monto negativo (suma agregada = 0; mismo patrón contable que doble entrada). **Trigger de cierre**: depende de qué requiere contabilidad — definir cuando llegue el bullet del commission engine + audit con contador.
- [ ] [diferido] **Rango `commission_pct ≤ 100` (CHECK actual)**: el constraint rechaza > 100%, pero v2 menciona "premios doble pago" (ej. bono semestral 200% sobre basis). ¿Flexibilizar el CHECK o usar `flat_amount` para bonos > 100%? **Trigger de cierre**: cuando v2 `commission_tiers` introduzca el caso explícito de premio multiplicador, posiblemente bumpear el CHECK a `≤ 500` o quitarlo.
- [ ] [diferido] **Trigger automático `commissions.status=PAID` → `promoters.total_commission_paid +=`**: relacionado con el primer item de V25. **Decisión**: depende de la resolución TRIGGER-vs-service del item correspondiente de promoters.
- [ ] [diferido] **Index strategy `(promoter_id, status, period_start)` vs partial por status**: hoy el partial es solo `WHERE is_active`. Si el 99% de queries son `status='PENDING'`, podría convenir partial adicional `WHERE status='PENDING' AND is_active`. **Trigger de cierre**: cuando haya volumen real de commissions, correr `EXPLAIN ANALYZE` sobre la query de liquidation; si bitmap heap scan domina, agregar el partial.

### V27 — `referrals`

- [ ] [diferido] **Uniqueness cross-table del `referral_code` (members vs promoters)**: hoy es **enforced application-side** (el resolver service-layer da precedencia al promoter table cuando hay colisión). ¿Promover a constraint DB con función custom o trigger que valide UNIQUE across (`promoters.referral_code`, `members.referral_code`)? **Trigger de cierre**: si en producción aparece una colisión real (admin asigna code a promotor que un member ya tiene), evaluar el costo del trigger vs el rework. Hasta entonces, service-side cubre.
- [ ] [diferido] **Default TTL para `referrals.expires_at`**: el schema permite NULL ("nunca expira"). ¿El service debe setear default (ej. 90 días desde creación) al INSERT de PENDING_ENROLLMENT? Si sí, ¿configurable per `referral_programs` (v2)? **Trigger de cierre**: definir antes de implementar `POST /v1/admin/referral-codes` o el job que expira PENDINGs vencidos.
- [ ] [diferido] **Multi-referral por payment**: el row de referral apunta a 1 payment (`reward_payment_id`); si un payment recibe descuento por N referidos diferentes del mismo afiliado, schema permite N referrals → mismo payment_id. Pero el payment NO captura el breakdown ("este pago se redujo $X por referral A, $Y por referral B"). **Trigger de cierre**: revisar cuando aparezca el caso real de stack de rewards; posiblemente tabla `payment_discounts` o columna JSONB en `payments` con el breakdown.
- [ ] [diferido] **Política de retry en generación de `members.referral_code`**: el service genera 6-8 chars UPPER alphanumeric con check de UNIQUE; ¿cuántos retries antes de fallar? ¿Aumentar charset si % de colisión alto? **Trigger de cierre**: monitoring post-launch — si la retry rate excede ~5%, bumpear longitud o ampliar charset.
- [ ] [diferido] **Cap de PENDING_ENROLLMENT por referrer**: schema no limita cuántas referrals pendientes puede tener un mismo affiliate. ¿Service enforce cap (ej. max 20 pendientes simultáneas) para prevenir spam? **Trigger de cierre**: revisar cuando un job de expiración detecte un patrón outlier (un solo afiliado con > N pendientes acumuladas), o cuando salga el dashboard del afiliado.
- [ ] [diferido] **Anti-recursión: el referido como referidor de su propio referrer**: si A refiere a B, y B luego refiere a A, ¿se permite? Hoy el schema solo bloquea `referrer = referred` (self), no el ciclo cruzado. **Trigger de cierre**: caso edge fraude (ring de 2 personas autoreferidas para acumular rewards); decidir si bloquear via CHECK constraint cross-row (trigger) o detectar via reporting de admin.
