- [x] [P0/C3] Invalidación de cache al cambiar status de membresía o aprobar/rechazar pago _(**`ValidatorCacheService`** en `modules/validator/service/` con clave canónica `validator:document:{type}:{number}` (single source of truth para producer + consumer del cache). API: `evict(documentType, documentNumber)` para invalidación explícita; `evictForMembership(Membership)` convenience que walks `membership → member → person`. **Redis-availability via `ObjectProvider<StringRedisTemplate>`**: cuando `auth.token-blacklist.provider=memory` (Redis auto-config excluido) el provider devuelve null y todo no-ops silencioso — degradación graceful en dev/single-node. **Failure policy**: Redis exceptions logueadas + swallowed; el row mutation upstream YA committeó, un hiccup de Redis no debe rollbackearlo. Worst-case: cache holds stale entry hasta TTL (60s spec), short-lived + self-healing. **5 trigger points** wired: `PaymentsService.approve` + `.reject` (después de applyReview, antes de email dispatch); `MembershipLifecycleService.cancel` + `.reactivate` (después de status set, antes del mapper); `MembershipStatusJobRunner.run` (per-transición en el loop, después de applyTransition + antes de fireNotification). El `MembershipStatusService` (date-driven evaluator) queda **pure** sin dependencia de cache — el runner orquesta. 7 unit tests en `ValidatorCacheServiceTest` cubriendo: happy path Redis delete con key canónica; evictForMembership walks chain; swallow exception; noOp cuando provider empty; skip null/blank document parts; noOp para broken chain (null member/person); `keyFor` shape. 90/90 tests verdes (+7).)_
