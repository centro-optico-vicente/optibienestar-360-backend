- [x] [P0/C3] `GET /v1/ally/validate/{document}` — cache Redis `validator:{document}` TTL 60s _(`AllyValidatorController.GET /v1/ally/validate/{document}` guardado por `ALLY_VALIDATE_MEMBER` (perm V6). **`ValidatorService.validate(document)`** flujo: (1) parse del path param `{document}` via regex `^([VEvVe])-?(\d{1,20})$` — acepta `V12345678`, `V-12345678`, `e-12345678` etc. case-insensitive (422 `validator.document.invalid` si no matchea); (2) lookup en Redis con clave canónica `validator:document:{type}:{number}` (mismo `cacheService.keyFor` usado por la invalidación — single source of truth producer/consumer); (3) si miss, walks `Person → Member → activeMembership` y resuelve estado; (4) graba al cache con TTL 60s + devuelve. **`ValidationResultDto`** flat record con enum `ValidationStatus { NOT_FOUND, NOT_ENROLLED, NO_ACTIVE_MEMBERSHIP, ACTIVE, SUSPENDED, EXPIRED, CANCELED }` + document type/number + member identity (uuid + fullName cuando found) + plan info (uuid/code/name cuando membership existe) + membership detail (uuid/enrolledAt/nextDueDate/lastPaidThrough/gracePeriodDays) + `cached` boolean diagnostic (cache hit ratio para monitoring). Solo `ACTIVE` autoriza al ally aplicar beneficio; los demás estados explican por qué (admin ve "suspendido por falta de pago", etc.). **Redis-availability defensiva** via `ObjectProvider<StringRedisTemplate>` — modo memory no rompe (no-op cache, llamada va siempre a BD). **Refinement sobre bullet text**: la clave es `validator:document:{type}:{number}` en vez de `validator:{document}` para evitar colisión de un V12345678 con un E12345678. **Mapeo lifecycle → validation**: switch-expression de `Membership.LifecycleStatus` a `ValidationStatus` (defensivo: status null o desconocido → NO_ACTIVE_MEMBERSHIP). DTO `@JsonInclude(NON_NULL)` para que campos vacíos no inflen payload del cache. 1 key i18n nueva en 3 bundles (validator.document.invalid). 90/90 tests verdes, contextLoads con beans nuevos.)_
- [x] [P0/C3] Invalidación de cache al cambiar status de membresía o aprobar/rechazar pago _(**`ValidatorCacheService`** en `modules/validator/service/` con clave canónica `validator:document:{type}:{number}` (single source of truth para producer + consumer del cache). API: `evict(documentType, documentNumber)` para invalidación explícita; `evictForMembership(Membership)` convenience que walks `membership → member → person`. **Redis-availability via `ObjectProvider<StringRedisTemplate>`**: cuando `auth.token-blacklist.provider=memory` (Redis auto-config excluido) el provider devuelve null y todo no-ops silencioso — degradación graceful en dev/single-node. **Failure policy**: Redis exceptions logueadas + swallowed; el row mutation upstream YA committeó, un hiccup de Redis no debe rollbackearlo. El `MembershipStatusService` (date-driven evaluator) queda **pure** sin dependencia de cache — el runner orquesta. 7 unit tests en `ValidatorCacheServiceTest` cubriendo: happy path Redis delete con key canónica; evictForMembership walks chain; swallow exception; noOp cuando provider empty; skip null/blank document parts; noOp para broken chain (null member/person); `keyFor` shape. 90/90 tests verdes (+7).)_
