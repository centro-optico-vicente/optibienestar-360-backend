- [x] [P0/C2] `V28__notifications.sql` _(Cola persistente outbound. **Por qué cola vs `@Async` fire-and-forget**: sobrevive restart JVM (no se pierde mail enqueueado en deploy), retry policy con exponential backoff visible en la row, audit trail per-recipient + per-source, admin queue UI puede mostrar "qué falló, por qué, reintentarlo". **Schema** (24 columns): channel CHECK 1-valor (EMAIL v1, extensible a SMS/PUSH con ALTER + CHECK update sin rewrite); recipient snapshot (`recipient_email CITEXT NOT NULL` capturado al enqueue para que cambios posteriores de email NO redirijan mail ya queueado + `recipient_user_id BIGINT NULL` FK opcional para navegabilidad + drill-downs + endpoint VIEW_OWN); locale (`recipient_locale VARCHAR(10)` default 'es' — pickea variante `*_es.html`/`*_en.html`); content (`template_code VARCHAR(80)` open sin CHECK whitelist — mismo patrón que `scheduled_jobs.code`, resuelve a Thymeleaf en classpath al render + nuevos templates landean por archivo no por migración; `subject VARCHAR(200)` pre-rendered al enqueue desde i18n bundle stored inline para replay sin re-resolver message keys; `template_vars JSONB` per-template para que cada template carry su shape — Hibernate 6 mapea con `@JdbcTypeCode(SqlTypes.JSON)` sobre `Map<String,Object>`); origin (`source_module VARCHAR(40)` + `source_entity_uuid UUID` — composite con `template_code` powers el idempotency check "ya enqueueamos `payment-approved` para este payment uuid?" sin necesidad de columna dedicada `idempotency_key`); lifecycle (status CHECK 5-valores: PENDING/SENDING/SENT/FAILED/DEAD_LETTER; `scheduled_for TIMESTAMPTZ` default NOW para future scheduled-at sends); retry policy per-row (`max_attempts` configurable: critical one-shot → 1, recordatorio rutinario → 5 service default; `attempt_count`, `last_attempt_at`, `next_retry_at` para exponential backoff 60s×2^(attempt-1) clamped a 1h, `last_error_message TEXT`); delivery outcome (`sent_at`); audit BaseEntity. **4 CHECK coherence**: (1) SENT ⇒ sent_at NOT NULL; (2) FAILED/DEAD_LETTER ⇒ last_error_message NOT NULL; (3) attempt_count ≤ max_attempts; (4) DEAD_LETTER ⇒ attempt_count ≥ max_attempts. **5 índices partial** (todos `WHERE` filtered para mantener chicos a escala — SENT + DEAD_LETTER son el bulk de la tabla a largo plazo): (a) `idx_notifications_pending_due (scheduled_for) WHERE status='PENDING' AND is_active` worker poll; (b) `idx_notifications_retry_due (next_retry_at) WHERE status='FAILED' AND next_retry_at NOT NULL AND is_active` retry poll separado del PENDING para no competir scans; (c) `idx_notifications_recipient_created (recipient_user_id, created_at DESC)` admin drill + VIEW_OWN; (d) `idx_notifications_source (source_module, source_entity_uuid, template_code)` pre-check idempotente al enqueue; (e) `idx_notifications_dead_letter (created_at) WHERE status='DEAD_LETTER'` triage admin del backlog. **Trigger** `set_updated_at()` reutiliza V2. **Permission catalog extendido**: dominio `NOTIFICATIONS` icono `i-lucide-bell` order 120; 3 perms `NOTIFICATION_VIEW_ALL`/`RESEND`/`VIEW_OWN`. **Distribución de grants** mirror exacto de `REFERRAL_CODE_VIEW_OWN` V6: SYSTEM + ADMINISTRADOR → 3 perms; AFILIADO + PROMOTOR + ALIADO → solo VIEW_OWN; OPERADOR* excluidos (actúan en nombre de otros, no reciben notificaciones personales). **Validación schema** corrida contra Postgres 15 real (DB ephemeral con V1+V2+V5+V6+V28 — skip V3/V7 que usan Flyway placeholders): 24 columns con tipos correctos (channel VARCHAR + recipient_email USER-DEFINED=CITEXT + template_vars JSONB), 5 índices partial visibles en pg_indexes, los 4 CHECK fire correctamente (SENT sin sent_at → reject, FAILED sin error → reject, DEAD_LETTER sin retries exhausted → reject, attempt_count > max → reject) + channel='SMS' → reject; happy paths (PENDING minimal, SENT con sent_at, DEAD_LETTER con 5/5) → accept. Local test profile sigue con Flyway disabled (H2 no parsea V1 extensions), CI corre full migration chain.)_
